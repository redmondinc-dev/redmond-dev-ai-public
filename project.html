Where we are

The registry is built and being filled in. We are finding out what already exists across Redmond — apps, APIs, MCP servers — before deciding anything about how it should be governed.

Running alongside that, we are working out what the lanes mean in practice and answering the governance questions underneath: who owns each data source, and who decides access.

Nothing changes for anyone yet. No approvals, no permissions, no new process. This phase is visibility only.

The plan

Phase 1A — Registry and Lane ModelKnow what exists, and publish what each lane means 3 of 6 done In progress

A catalogue of anything built or used at Redmond, and the model that says what each thing is allowed to do. The registration threshold is whether something touches company data — if it does not, there is nothing to register.

Seed the RegistryJeremiahDEVSTD-3

As the project team, I need the registry populated with what already exists so that we know what is running before we try to govern it.

Acceptance criteria
  • Register apps, third-party APIs, APIs we build, MCP servers, and connectors
  • Include anything under development, partially built, or not currently in use
  • Capture owner, purpose, data touched, and where code and documentation live
  • Reference credentials by location only — none stored in the registry
  • Create entries from the template so the summary tables populate
  • Apply the registry label by hand in Confluence or the entry will not appear
  • Follow up with builders surfaced during seeding
Ratify and Publish the Lane ModelKirtDEVSTD-22

As an employee building at Redmond, I need to know which lane my project falls into so that I understand what is expected of me without having to ask.

Acceptance criteria
  • Settle the lane count — three, four, or merge lanes feeding into two and three
  • Decide whether Lane 1.5 is its own lane or an on-ramp within Lane 1
  • Confirm lane definitions are based on what an app needs and touches, not who built it
  • Publish escalation triggers as tests a builder can apply to themselves
  • State the registration threshold — anything touching company data
  • Publish in plain language where builders will find it
Evaluate Existing Redmond SolutionsPhilDEVSTD-23

As the project team, I need to know whether existing Redmond tooling can serve as the registry and build path so that we extend what works instead of rebuilding it.

Acceptance criteria
  • Evaluate existing MCP servers, project starter tooling, and pre-provisioned sandboxes
  • Produce a written gap list against what Phase 1A requires
  • Recommend whether to adopt, extend, or build fresh
  • Decide one MCP server or separate servers for data and application development
  • Agree the improvement route with the solution's owner rather than assuming it
  • Report findings to the working group before build work starts

Phase 1B — AI Governance DiscoveryUnderstand the problem before proposing an architecture 0 of 2 done In progress

Runs in parallel with 1A, not after it. The instinct has been to jump to answers — restrict it in the MCP server, enforce at the data layer, buy a tool. None of that is ready to be decided, because the questions underneath are not answered.

Data Source Ownership and Access Decision RightsKirtDEVSTD-27

As the AI governance group, I need a named owner and decision maker for each data source so that access requests have somewhere to go.

Acceptance criteria
  • Name an owner for each significant data source — HR and time, Paylocity, Fabric, Acumatica, warehouse
  • Decide whether each owner decides directly or routes to stakeholders
  • Document what an owner can decline alone and what escalates
  • Assign ownership of Acumatica roles and permissions
  • Confirm with each named owner that they accept the role
Default Access Posture and the Sensitive Data Exception ListUnassignedDEVSTD-28

As a Redmond associate, I need to know what data I can use by default so that I am not asking permission for information I should already have.

Acceptance criteria
  • Publish the default — company data is open to associates and their AI agents
  • Define the sensitive exception list, starting with HR data (pay rates, birthdays) and Paylocity API access
  • Confirm the exception list with HR
  • Agree who approves an exception and who it escalates to
  • Document what an associate can expect without asking

Phase 2B — Lanes Established and SupportedRun the model in practice Not started Next

A published model changes nothing on its own. Lanes get assigned to real things, support paths get named teams behind them, and the first apps actually move between lanes so we learn where it breaks. Lane 3 already works. Lane 2 is the gap — a useful tool that people depend on, with no clear answer on who picks it up when the owner is unavailable.

No stories yet — scoped once the lane model is ratified.

What is still open

  • How many lanes. Three, four, or merge lanes feeding into two and three. Needs settling before the model is published.
  • Who owns and runs the registry long term. It needs a maintainer and renewals need a reviewer. Raised repeatedly, not assigned.
  • Who approves a data access exception. The default is settled — open, except sensitive HR data and Paylocity. The decision rights are not.
  • Acumatica roles and permissions. Pending since 2019. The role structure is a base that applies almost everywhere else.
  • Timeline and budget. No target date or estimate yet.
